# v0.1.0 scope

Status: approved by the project owner, 17 Nov 2026. Read with [VISION.md](VISION.md). Every queue item and every pull request must name one item id from this page. Work that names none is not agreed work. Current progress against this plan is listed in [ROADMAP.md](ROADMAP.md).

v0.1.0 is the single-node queue release: the queue, its claims and its holds are decided on one machine, with many agents. It is tagged at the end of the two-week window (1 Dec 2026) when every must-have below is met. That means the queue items (M1 to M8, M10) on the owner's Mac, and also the Mac and the VPS paired and syncing as M9 describes. M9 is a tag requirement, not an option. Cross-node queue claims ship as v0.2.0.

"The owner" on this page is the project owner. "Admit" means the owner, or an architect the owner delegates to (see How work is done).

Lines marked *(architect's call)* were filled in by the architect and accepted by the owner in review.

## Must have

| Id | Item | Done when |
|---|---|---|
| M1 | **Queue with admission.** States: proposed, ready, claimed, done. Anyone proposes. Only the owner or the delegated architect admits, and a ready item has a scope id, a done condition and that approval, recorded with who admitted it and when. `next` hands one ready item to one agent atomically, and refuses an agent that already holds its limit of claimed, unfinished items; the owner sets the limit. Security and data-loss findings go to the owner personally for a fast yes or no, and still wait for it. | Fifty agents racing for `next` never get the same item. A proposed item cannot be claimed by any path (CLI, MCP, remote). An admitted item shows its approver and the time. An agent at its limit is refused by `next` with a message that says why. The owner's fleet runs from this queue, not a markdown file, for at least 3 consecutive days with at least 3 agents and zero lost or duplicated items, checked from the event log. |
| M2 | **Durable record of claims, handoffs and results.** Each is an event. A result is stored on its item: a short summary plus a pointer (pull request, commit or file). A claim returns to ready, with its history, only on a confirmed session end (the session-end hook ran, or the transport reports the agent unreachable or gone) or after a long grace period with no sign of life. Missed heartbeats alone never release a claim, because an agent that is thinking for a long time or is rate-limited is still working. The original agent is told its claim was released. Holds keep their shorter expiry rule. *(architect's call: the grace period defaults to 24 hours and the owner can change it.)* | Killing a pane mid-item leaves the item claimable by another agent with the earlier claim and notes visible. An agent that is silent but alive for an hour keeps its claim. A released claim produces a message to the agent that held it. No result exists only in a lane file. |
| M3 | **Upgrade safety.** A backup is taken before any migration. A build refuses a database with a newer or unknown schema and says how to fix it. `another doctor` flags a mismatch between the installed build and the database. A development build refuses to migrate a home it did not create unless told to explicitly. *(architect's call)* Schema numbers are assigned by the architect at merge time; lanes do not reserve them. | The 17 Nov failure (a dev build migrating the live home and breaking holds) is reproduced in a test and refused. The live `~/.another` runs on an installed build that matches its schema. |
| M4 | **Path holds that hold.** The edit hook takes and enforces holds for Claude Code and Codex, inside each working directory on one machine; worktrees and clones are separate and never block each other. No new hold features; admitted fixes only. | Existing behaviour on `main`, with every admitted hold bug closed. |
| M5 | **Transport adapter interface.** Starts with three operations and may grow by reviewed spec: `wake(agent, message)` reports whether it was delivered and whether the agent started working; `status(agent)` reports working, idle or done, blocked on a person, or unreachable or stuck; `list()` reports the agents the transport can see. Two adapters: Herdr, and a generic command adapter that maps the operations to configured shell commands. Reading panes and sending keys stay in the transport. | A wake that is delivered but does not start work is recorded as failed and shown. Agents that vanished from the transport are noticed. The nudge-adapter PRD is rewritten against this interface, not patched. |
| M6 | **Hook packs for Claude Code and Codex.** At each turn the agent sees message and queue updates, with no transport needed. | A fresh session on each client, with no Herdr, learns of a new message and a ready item within one turn. |
| M7 | **Seeing stuck work.** One place lists what needs the owner: agents blocked or stuck, failed wakes, and proposed items and other decisions awaiting the owner. `another doctor` also runs the read-only scan for lapsed resources and unregistered listeners. `board` and `stats` stay as they are, except that a shared read-only open for `board` and `needs` is admitted (M-X, #319). | The owner can answer "what is waiting on me" and "what is stuck" with one command each. |
| M8 | **Daemon on macOS and Linux.** Runs wake and expiry in the background. | Installs, restarts and reports status on the Mac and on the VPS. |
| M9 | **Hub and spoke as it exists today, between the Mac and the VPS.** Messages, holds and activity sync over Tailscale or a tunnel. The hub is backed up on a schedule. Fixes to this path are admitted case by case. | The Mac and the VPS are paired and syncing; a hub backup has been restored once as a test. |
| M10 | **A release people can install.** Tag, macOS and Linux archives, and a README, quickstart and AGENTS.md that describe this scope. Frozen features are marked experimental. | Install from the archive on a clean machine following the README works. |

## v0.2.0: cross-node queue (not in this release)

Recorded here so v0.1.0 work does not block it. It ships when it has run across the owner's nodes (Mac, VPS hub, second machine) without loss.

- Every queue item has a home node. Local items are claimed without the hub; shared items are arbitrated by the hub.
- Each connected spoke leases a small batch of ready shared items in advance and keeps claiming from it when the hub is unreachable. Batch leases do not expire on a timer; unused ones return on reconnect, and only the owner can revoke a batch.
- Holds split the same way: local repos are enforced locally, shared paths by the hub.
- A cut-off spoke keeps working, records locally, syncs on reconnect and shows "hub unreachable".
- This replaces D24 (requests are node-local) and D26 (cross-node hold clashes are only warnings).

## How work is done

- No pull request without a ready queue item. A finder records the finding as a proposed item and moves on.
- Independent review only. Nobody reviews or merges their own work. No force pushes, no admin bypass.
- A development build never runs against the live `~/.another`. Use `ANOTHER_HOME=$(mktemp -d)`.
- Admission belongs to the owner, or to an architect the owner delegates to (currently Fable, the project's architect agent). Security and data-loss fast-lane items always go to the owner personally.
- The architect plans; about three workers implement; the owner tags.
