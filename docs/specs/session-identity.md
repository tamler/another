# Spec r5: distinct agent identity per session

Status: draft, not independently reviewed or approved for implementation. Baseline: `0403dce40567190d37007bef1f4096987501ee2f`.

## Problem

At this baseline `hook_agent` in `crates/another/src/hooks.rs` uses `ANOTHER_AGENT` verbatim or registers `client@project`; `known_agent` repeats that lookup. `HookInput` parses `session_id`, `sessionId` and `conversation_id`, but the resolved identity does not use those values. Two concurrent panes using the same address can therefore be treated as the same hold owner. Identity also controls messages, presence, keepalive, wake targets and session end, so changing only the edit guard would leave inconsistent authority.

## Desired behavior

Each supported hook event resolves to a distinct canonical session address within a project. Concurrent sessions sharing a base name conflict on exclusive holds. A resumed client reuses the address only if it actually supplies the same session ID. A pane ID alone is not globally unique and cannot distinguish two sessions in one pane. CLI and Git commands require the explicit binding below; hook stdin cannot modify the parent shell.

## Proposed identity contract

- Hook `ANOTHER_AGENT` is a base, not the final actor. Validate its name and require any explicit project to match the resolved hook project; otherwise use the effective client name. CLI `--agent` and non-hook `ANOTHER_AGENT` remain exact actor addresses and are never silently rewritten. Deliberately sharing an exact CLI actor retains existing shared ownership and is not session authentication.
- Require a top-level effective-client session ID: nonempty UTF-8, at most 512 bytes, no control characters. Serialize a version tag and length-prefixed local node ID, effective client, canonical project ID, validated base name and session ID; SHA-256 this tuple. The name is the first at most 30 ASCII bytes of the base, `-s`, then the first 32 lowercase hex digits of the digest, at most 64 characters. New hook processing never displays, logs or stores the raw session ID or puts it in the address; the historical limitation below is explicit.
- In one write transaction register/find the actor and bind the full tuple digest, validated base, project and effective client to it; require uniqueness of both full digest and actor address. If a truncated digest collides with another full digest or an unrelated existing actor name, fail visibly and never alias or overwrite it. Concurrent starts for the same tuple converge. A Start, Prompt, PreEdit, PostTool and End with the same tuple all resolve to the same actor. No automatic actor reap.
- A missing, malformed or inconsistent session ID never falls back to a shared base. A matched pre-edit emits the client's verified deny response and an actionable message; other events emit bounded diagnostics and never renew or release anyone's holds. A client is supported only after real tests establish its fields on every relevant event and its denial response. IDs are opaque identifiers, not authentication; this guards cooperating local processes, not malicious same-user processes or MCP callers who can assert actor arguments.
- Start's digest displays the full address. `another session exec --agent <full-session-address> -- <program> [args...]` verifies it is a local session actor and runs a child with exact `ANOTHER_AGENT`, preserving argv without a shell. CLI and Git children inherit it; alternatively pass the full address or export it explicitly. If a hook sees an address registered as a session actor in `ANOTHER_AGENT`, it retrieves that actor's recorded base and recomputes the tuple using the current event's session ID, client and project; only an exact digest/address match may reuse it. A mismatch denies the pre-edit and other events cannot act for it; do not suffix an already suffixed address again or accept a caller's assertion as proof. This helper is convenience, not proof that its caller owns the session. A Git guard must not infer a session from a base or pane name. Mail at the base stays there; no copying, forwarding, transfer or deletion. New mail targets the session address. Herdr wake needs an actually captured pane target, never a guess from the suffixed name.
- A client can resume with the same session ID, and an incoming hook Start, Beat or End does not prove which incarnation sent it. Until a client supplies a separately verified incarnation fence on every lifecycle event, none of those hook events releases or renews holds or resources, changes presence, captures, replaces or clears a wake target, resets waits, or alters an admission. Start may resolve/register the actor and display its digest, without consuming an announcement whose client cannot display it. The user can explicitly set a wake target for the exact actor through the existing manual wake command; automatic session capture is disabled for unfenced session actors. Pre-edit can take or renew a narrow hold for its requested paths. Without such activity holds expire under their existing TTL. A delayed Start, Beat or End cannot affect a successor, but a finished session may leave a temporary blocker until TTL expiry or explicit manual release. This limitation supersedes automatic hook lifecycle side effects for these session actors; explicit CLI/MCP `heartbeat --end` remains an intentional exact-actor operation and is documented as such. Never infer a fresh incarnation from arrival order or a local counter alone. Preserve explicit human approval for reaping. Old session identities, mail and holds remain intact. A task capability and fenced handoff belong to the lifecycle spec, not the address.
- Imported and native Grok routes must not both execute the same pre-edit admission against the same correlation ID: an ambiguous duplicate cannot safely replay an allow. The separately reviewed agent-hooks and DB contracts must select and prove one route or conservatively deny where route ownership cannot be established; identity rollout must not claim safe duplicate routing until those contracts are reconciled and tested. No rule here suppresses a proven conflict denial.

## Session events and historical data

At the baseline, hooks put the raw ID in `SessionInfo`, start/end write it in signed `session.started` and `session.ended` event payloads (`holds.rs:1031-1052`), and activity exposes it (`activity.rs:262-275`). Change the hook path so that after tuple hashing no raw ID enters `SessionInfo`, persisted session bindings, diagnostic text or events. New session lifecycle events retain `agent_id` and client and set `session_id` to JSON null for compatibility; include the versioned full tuple digest under a distinct `session_fingerprint` field. The digest is an identifier, not a secret or authorization. The core must enforce the same rule for CLI, MCP and any other callers of session lifecycle methods, not just the hook path: accept no caller-supplied raw session ID into a persisted event; either derive the fingerprint through the same validated context or use null when no validated session exists. Do not hash arbitrary raw inputs in a way that conflates different nodes or clients. Activity, dashboard and normal projections show the actor and optional fingerprint, never a raw session ID. New local events therefore carry no raw ID in event listing, dashboard, MCP output or signed federation payload. Audit all consumers and tests of `SessionInfo` and session-event payloads, including activity, event CLI/JSON, dashboard, federation export/import and sync, so none logs the incoming raw hook payload or reintroduces a raw ID in new local events.

Do not rewrite, delete or re-sign existing signed events. Historical local or imported events can already contain raw IDs; preserve their exact signed bytes and chain. Activity and dashboard projections redact the legacy `session_id` field, but raw event listing, federation replication and authorized database access may still expose historical payloads, and older peers may continue sending raw IDs. Document that limitation before rollout; do not claim historical removal or prevent replication by silently rewriting signed bytes. A separate explicit history-retention and federation decision is required before any destructive scrub. Newly received legacy events retain their original signatures and receive the same redacted activity/dashboard projection; raw protocol fidelity remains an explicit exception to the new-event privacy guarantee.

## Migration and selected defaults

Use the next unused schema migration after the actual integration head; never rewrite an applied migration. Existing `open_quick` rejects schema mismatches and older clients can use a shared identity or fail open, so mixed old/new writers cannot claim exclusivity. Before backup or migration, the operator establishes and verifies a quiescent writer fence: stop only operator-identified owned daemon, clients, hook and MCP processes, prevent new writers from starting, and verify no remaining connection or process can open the home for writing. If that cannot be established, stop the rollout. With the fence held, use SQLite's online backup API against the quiescent source to create a complete consistent database snapshot including committed WAL content; include the node identity and all other required home metadata in the protected backup. Check the backup API result, run `PRAGMA integrity_check` on the backup, verify required metadata and record the snapshot's schema version and hashes. A copy of the main database file alone is not a backup. Keep the fence held while migrating once and installing the matching binary and wrappers, then restart clients and verify versions and two independent sessions. This spec does not authorize live installation or process termination.

For interrupted upgrade or downgrade, first fence writers again and preserve an intact copy of the current home. Restore the verified database and matching metadata into a separate staging home, run integrity and identity checks there, then replace the live home only with explicit operator action. A snapshot cannot contain writes committed after it: if any post-snapshot writes occurred, do not overwrite them or claim they survived; preserve the newer home and require an explicit reviewed reconciliation or abandonment decision before replacing it. Record the source snapshot and any intervening writes. No owner choices remain for normal operation; supported client/version claims still require evidence.

## Acceptance evidence

- Unit tests pin tuple encoding, digest and name length, validation, concurrency and collision refusal. Use a distinctive raw session ID in start and end through actual dispatcher paths and assert it is absent from new event storage, activity, dashboard, CLI/JSON, MCP, diagnostics, logs, address and signed federation export. Exercise core CLI/MCP lifecycle entry points as well as hooks. Inject a signed historical event with that ID, verify its stored bytes and signature are unchanged and activity/dashboard redact it, and show raw event listing and federation retain the disclosed historical limitation. Test legacy incoming event projection and ensure no new local event is generated with raw ID. Test missing ID and collision denial through `run_fail_open`, not just the resolver, and assert other events cannot release another actor.
- Two real simultaneous sessions with the same base edit the same file: first holds it and second is denied; distinct files proceed. Test same pane, parallel initialization, changed and stable resume IDs, project mismatch, termination, legacy mailbox and holds, exact CLI actor and session-exec Git child propagation. Test old/new mixed-version limitation and interrupted migration. Reproduce old hook Start and End events delayed until after a same-ID resumed Start, new hold, manually set wake target, admission and wait: no successor state is released, reset, renewed, redirected or marked offline. Test both orders of duplicate routes, idle expiry and explicit exact-actor manual End. Show that an explicitly set wake goes to the selected pane and an old Start cannot redirect it. Exercise duplicate native/imported pre-edit IDs, ambiguous admission and missing routes against the integrated admission design; do not claim Grok support until that design passes review and live tests.
- Verify CLI, Git hook, edit hook, wake and mailbox behavior in each supported client; explicit overrides, absent/malformed IDs and concurrent registration are covered. Demonstrate visible failure when identity cannot be propagated.
- Exercise macOS, Linux, native Windows and WSL, including environment inheritance boundaries and separate hook processes. Unit tests establish deterministic mapping and database uniqueness; real integration runs establish actual propagation and blocking behavior. Mark any untested client or platform unsupported rather than assuming parity.
- Test WAL snapshot with committed content, writer-fence refusal, integrity verification, staged restore, interrupted upgrade and a post-snapshot write; prove restore does not overwrite newer data without an explicit operator decision. The first identity phase remains exposed to baseline database and wrapper fail-open behavior until the separately reviewed DB-lock phase ships; a resolver-level deny alone does not establish real client enforcement. Record wrapper, client, OS and version evidence separately. Run repository CI checks and obtain independent spec review before any build lane.
