Install with Cargo

No GitHub Release has been published yet. Use Cargo until the first release is available or if the prebuilt install fails.

You need Rust 1.88 or newer, its Cargo tool and a C compiler. Step-by-step prerequisites are on the pages for macOS and Linux. The Windows page covers experimental native setup and WSL 2.

cargo install --locked --git https://github.com/tamler/another another
another --version
another --help

Cargo normally installs into ~/.cargo/bin. Include that directory in PATH for both your terminal and your coding client. For updates from the repository, repeat the install command with --force.

Prebuilt binaries from the first release

From the first release, run this on macOS or Linux:

curl -fsSLO https://github.com/tamler/another/releases/latest/download/install.sh &&
  sh install.sh

The script defaults to the latest release. Pass a version or tag, such as sh install.sh v0.1.0, to select that release once it exists. Before the first tag, the interim script on main prints the Cargo fallback.

The script verifies the archive and installs into ~/.local/bin. Set ANOTHER_INSTALL_DIR to choose a different directory and make sure it is on your PATH.

You can also run cargo binstall --git https://github.com/tamler/another another or download an archive from GitHub Releases. The workflow packages macOS and static musl Linux binaries for x86_64 and arm64, plus a Windows x86_64 zip. Verify a manual download before unpacking it, then put the binary on your PATH.

On macOS, a verified download may need its quarantine attribute removed:

xattr -d com.apple.quarantine ./another

Build from source

git clone https://github.com/tamler/another
cd another
cargo build --release --locked
# Install the binary somewhere outside the Cargo build directory:
cargo install --locked --path crates/another --force
another --version

The build output is target/release/another, but treat that as a development build: do not point an MCP client at it or run it against a live ~/.another. Install the binary (for example with cargo install --path crates/another, as above, or by copying it to a directory on your PATH) and configure MCP clients to run the installed another command.

Verify a release archive

For the Windows zip, use the PowerShell verification steps. Release archives are unsigned. A matching SHA-256 confirms that the download matches its checksum file.

Archives are named another-VERSION-TARGET.tar.gz. The target is aarch64-apple-darwin, x86_64-apple-darwin, x86_64-unknown-linux-musl or aarch64-unknown-linux-musl. Each archive's checksum is in a file with the same name plus .sha256.

Put the archive and its .sha256 file in one folder and change to that folder. Set archive on the first line to your file's name, then paste:

archive=another-0.1.0-aarch64-apple-darwin.tar.gz
expected=$(awk -v file="$archive" '$2 == file { print $1 }' "$archive.sha256")
actual=$(sha256sum "$archive" 2>/dev/null || shasum -a 256 "$archive")
if [ -n "$expected" ] && [ "$expected" = "${actual%% *}" ]; then
  tar -xzf "$archive" && echo "Verified and unpacked: $archive"
else
  echo "FAILED: do not install $archive"; false
fi

It hashes the archive with sha256sum where that is installed, or shasum -a 256 otherwise, and compares the result with your archive's line in its .sha256 file. It compares the values itself because sha256sum -c on some macOS versions exits successfully when it finds no line it can read.

A match prints Verified and unpacked and unpacks the archive into a folder of the same name. If you see FAILED, nothing is unpacked. Stop there and delete the download; do not install it.

No release exists yet, so this snippet has only run against local fixture archives built the way the release workflows build theirs. Every site build repeats that test. If you would rather run shasum -a 256 -c or sha256sum -c by hand, docs/VERIFY.md shows both, with the exit status on a match and on a tampered archive, recorded against a fixture.

Replace a binary safely on macOS

Remove the old executable before copying the replacement into its place. Overwriting it in place can leave a stale code signature cached and cause macOS to kill the new process at launch. Cargo's installer handles replacement safely.

Replace the executable only. Keep ~/.another (or your ANOTHER_HOME) intact: that directory contains your node's data. Stop and restart your own Another daemon after updating so it uses the new binary.

Check your first run

another --version
another init
another status

If your client cannot find the binary, compare its configured command and PATH with the working terminal. Then connect hooks and MCP and send your first message.
