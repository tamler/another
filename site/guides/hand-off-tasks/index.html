Hand off a task with an owner

A message asks. A request records who took the work, and whether it finished.

Getting started Install What is a request?

Open a request

Run from one physical repository root. These are demo identities. --request opens a claimable request with the message; --due sets a deadline in seconds and implies --request.

another init
another agent register lead --program claude --project .
another agent register worker --program codex --project .
another send --from lead --to worker --subject "Fix the flaky test" --body "See tests/net.rs" --due 3600
another requests --status open

send prints the request ID, and another inbox --agent worker shows it too. Examples below write it as REQUEST_ID; substitute the real one.

Claim it before starting

another request claim --agent worker REQUEST_ID
another requests --owner worker

A claimed request has one owner. A second agent trying to claim it gets an error naming the owner, and the command exits with status 1. Reading or acknowledging the message does not claim the work.

Finish it, or give it back

another request complete --agent worker REQUEST_ID --note "Fixed in the retry branch"
another request release --agent worker REQUEST_ID --note "Blocked on the fixture"

These are alternatives. complete marks it done and mails the requester a Done: message. release puts it back to open for someone else. Only the owner can complete a claimed request. Once done, it can't be claimed again.

Only the agent that opened a request can cancel it. Being a recipient isn't enough.

another request cancel --agent lead REQUEST_ID

When work goes quiet

A request past its due time becomes stale, and any agent may take it over, even from its current owner. Stale doesn't mean abandoned; the first owner may still be working. Check with them, or check another activity, before you take it.

another sweep
another requests --status stale
another request claim --agent lead REQUEST_ID

A running another serve sweeps every 30 seconds by default. Without one, another sweep applies the change at once. A claim can set a new deadline with --due; a takeover without one clears the old deadline.

Received is not done: a recorded run

An ack records receipt. A claim records an owner. Only complete records that the owner says it finished, and only you can check that it did. This run was captured from another 0.1.0 built from 5ec0a58 (then main) against a temporary project named shop, with no hooks and no server. Ids are as recorded. The same walkthrough is in the repository at docs/REQUESTS.md.

The lead opens work with a deadline. The worker acks the mail: awaiting ack drops to 0, and the request is still open with no owner.

$ another send --from lead --to worker --subject "Fix the flaky test" --body "See tests/net.rs" --ack --due 900

$ another ack --agent worker 01M77HNNED9HZY6CKDHEZTPNSS

When the worker comes back, complete marks the request done and mails the lead a Done: message in the original thread. The note is the body; without one it reads Request <id> is done. That mail is the only thing the sender's inbox receives about the request.

done      worker@shop      Fix the flaky test  (from lead@shop due 2026-11-12T09:48:24.813Z)  [01M77HNNEDVZ92ZVSKQEYXYRB5]
$ another inbox --agent lead

   new  2026-11-12T09:33:24.901Z  worker@shop      Done: Fix the flaky test  [01M77HNNH6XPXEDYZ664XR2PKY]

If instead the worker never comes back, the deadline does the work. This third request was opened with --due 5. The worker acked, claimed, and stopped. Past its due time it is stale: another sweep applies that at once, and another requests and another inbox sweep before they list. A stale request keeps its owner, so another agent cannot release it. Takeover is a claim, and the Done: mail names who finished it.

A request opened without --due never goes stale on its own. If its owner stops, it stays claimed until the owner releases or completes it, or the creator cancels it. Set a due time on work you may need to take over. Nothing watches the worker: a crash leaves the request exactly as it was, and nothing is pushed to anyone when it goes stale.

What a request doesn't do

  • It doesn't assign. When sent to several recipients, one request opens and whoever claims first owns it.
  • It doesn't check the work. complete records a claim of completion. Review the result yourself.
  • It doesn't deliver itself. Hooks announce it at the next session start, tool call or prompt, and wake adapters can nudge an idle terminal.
  • It doesn't cross machines. Requests stay on one node. Sending one to an agent on another node fails; send plain mail instead.

MCP clients do the same through send_message with create_request and claim_request with an action. MCP messaging shows the arguments.
