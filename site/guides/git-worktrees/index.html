Agents in separate git worktrees

Worktrees keep their files apart. Another lets them talk, with one catch about holds.

Getting started Install What is a project?

The catch: each worktree is its own project

Another identifies a project by its directory, so it doesn't know two worktrees share a repository. Here is what that means with two worktrees, shop-parser and shop-ui, on one machine using the same ~/.another:

What crosses between worktrees on one node
FeatureAcross worktrees
Mail and requestsYes. Same node, so any agent can reach any other
Activity feedYes. It covers the whole node
ResourcesYes. Listings aren't limited to a worktree unless you pass --project
Path holdsNo. A hold in one worktree does not conflict with the other

That last row usually matches reality. Each worktree has its own files, so editing src/app.rs in both is not an immediate collision, and a clean hold check only says that no one holds it in that project. The clash, if there is one, arrives as a merge conflict.

Talk across worktrees

Run from the root of each worktree. --project . scopes the name to that worktree. A session's hook does the same thing automatically, naming it after the client and the nearest directory containing .git, such as codex@shop-ui.

another init
cd ../shop-parser
another agent register parser --program claude --project .
cd ../shop-ui
another agent register ui --program codex --project .
another send --from ui --to parser --subject "API change" --body "Renamed fetch_user on my branch."
another inbox --agent parser

Bare names work while they are unique across the node. Once you run claude in two worktrees, claude alone is ambiguous and the command tells you the choices. Use the full form, like claude@shop-parser. Folders with the same name, such as a/shop and b/shop, get slugs like shop and shop-2; another project list shows them.

This is a good use of mail: tell the other worktree when you change something it depends on, before the merge finds it.

If you do want shared holds

Sometimes you want one claim across every worktree, such as "I'm reworking the migrations, stay out". Register the agents and take holds against one common project: pick the main checkout's path, or its slug once registered, and use it from everywhere. The path here is an example.

another hold acquire --agent ui --project ~/work/shop 'migrations/**'
another hold check --agent parser --project ~/work/shop 'migrations/001.sql'

Both agents need to be registered and to use the same --project value. The check exits with status 3 on a conflict. The holds still don't touch your files or stop a commit; this only makes the intent visible. Without that flag, hold commands use the current directory, so an agent that forgets it checks its own worktree and sees no conflict. That is a false reassurance if you were counting on the shared scope.

What this page rests on

We ran these with real git worktree checkouts and the CLI on one machine, and saw the behavior in the table: mail delivered, no hold conflict across worktrees, and status 3 under a common project. Hook-created names are from the hook documentation, not from a client session in a worktree.
