Agents in separate git worktrees

Worktrees keep their files apart. Another lets them talk, and its holds do not block across them (holds are per checkout).

Getting started Install What is a project?

Each worktree is its own project, and holds do not block across them

Another identifies a project by its directory, and it also links each project to its repository, read from the origin remote or the shared git directory without running git. Here is what that means with two worktrees, shop-parser and shop-ui, on one machine using the same ~/.another:

What crosses between worktrees on one node
FeatureAcross worktrees
Mail and requestsYes. Same node, so any agent can reach any other
Activity feedYes. It covers the whole node
ResourcesYes. Listings aren't limited to a worktree unless you pass --project
Path holdsNo. Holds block only within one checkout (one working directory). Holds in other worktrees are listed as other checkout and never block

That last row is on purpose. Each worktree has its own files, and holds are scoped to a single checkout to avoid blocking parallel work. If you want a heads-up anyway, list holds (another holds) and watch for ones marked other checkout before you start editing the same path in two worktrees.

Talk across worktrees

Run from the root of each worktree. --project . scopes the name to that worktree. A session's hook does the same thing automatically, naming it after the client and the nearest directory containing .git, such as codex@shop-ui.

another init
cd ../shop-parser
another agent register parser --program claude --project .
cd ../shop-ui
another agent register ui --program codex --project .
another send --from ui --to parser --subject "API change" --body "Renamed fetch_user on my branch."
another inbox --agent parser

Bare names work while they are unique across the node. Once you run claude in two worktrees, claude alone is ambiguous and the command tells you the choices. Use the full form, like claude@shop-parser. Folders with the same name, such as a/shop and b/shop, get slugs like shop and shop-2; another project list shows them.

This is a good use of mail: tell the other worktree when you change something it depends on, before the merge finds it.

Holds across checkouts

Holds block only inside the checkout they were taken in. A hold in one worktree never blocks edits in another worktree, even when both worktrees are for the same repository.

cd ../shop-ui
another hold acquire --agent ui --project . 'migrations/**'
cd ../shop-parser
another hold check --agent parser --project . 'migrations/001.sql'
no conflicts

The check exits with status 0, and the edit hook does not deny an edit based on a hold in another worktree. another holds --project . still lists holds in sibling checkouts and marks them as other checkout:

exclusive ui@shop-ui-2     shop-ui:migrations/**  until 2026-11-22T19:07:42.197Z  [01M828SFDPEAJS9V2CTBCWH5ZX]  other checkout
other checkout: taken in a different working directory from this one; it does not block edits here

An edit from a shell command still gets through, and nothing guards a commit. Holds on other machines are matched by project name and reported as warnings, never conflicts.

What this page rests on

We ran these with real git worktree checkouts and a build of main on one machine, in temporary state: mail delivered; a hold taken in one worktree did not make hold check fail in the other (it printed no conflicts and exited 0); another holds listed the hold and marked it as other checkout; and a shell write to a file is still unguarded. Hook-created names are from the hook documentation, not from a client session in a worktree.
