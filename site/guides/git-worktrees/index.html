Agents in separate git worktrees

Worktrees keep their files apart. Another lets them talk, and its holds cross them.

Getting started Install What is a project?

Each worktree is its own project, and holds still cross them

Another identifies a project by its directory, and it also links each project to its repository, read from the origin remote or the shared git directory without running git. Here is what that means with two worktrees, shop-parser and shop-ui, on one machine using the same ~/.another:

What crosses between worktrees on one node
FeatureAcross worktrees
Mail and requestsYes. Same node, so any agent can reach any other
Activity feedYes. It covers the whole node
ResourcesYes. Listings aren't limited to a worktree unless you pass --project
Path holdsYes. A hold in one worktree conflicts with the same path in the other, and the edit hook stops the edit

That last row is on purpose. Each worktree has its own files, so editing src/app.rs in both is not an immediate collision, but it is a merge conflict waiting to happen. The hold says so before the second agent writes.

Talk across worktrees

Run from the root of each worktree. --project . scopes the name to that worktree. A session hook uses the client, session ID and nearest directory containing .git to derive a distinct actor; its start digest shows the full address.

another init
cd ../shop-parser
another agent register parser --program claude --project .
cd ../shop-ui
another agent register ui --program codex --project .
another send --from ui --to parser --subject "API change" --body "Renamed fetch_user on my branch."
another inbox --agent parser

Bare names work while they are unique across the node. Once you run claude in two worktrees, claude alone is ambiguous and the command tells you the choices. Use the full form, like claude@shop-parser. Folders with the same name, such as a/shop and b/shop, get slugs like shop and shop-2; another project list shows them.

This is a good use of mail: tell the other worktree when you change something it depends on, before the merge finds it.

Holds across checkouts

Holds are compared by repository-relative path across every local checkout of the same repository: sibling worktrees, and separate clones of one origin. Take the hold in your own worktree, and the check in the other one sees it:

cd ../shop-ui
another hold acquire --agent ui --project . 'migrations/**'
cd ../shop-parser
another hold check --agent parser --project . 'migrations/001.sql'
conflict: migrations/001.sql is held by ui@shop-ui (shop-ui:migrations/**, exclusive until 2026-11-12T10:14:45.075Z)

The check exits with status 3, and with the hooks installed, the edit hook stops parser's client edit of that file and names ui@shop-ui. another holds --project . lists holds in sibling checkouts too. An edit from a shell command still gets through, and nothing guards a commit. Holds on other machines are matched by project name and reported as warnings, never conflicts.

What this page rests on

We ran these with real git worktree checkouts and a build of main on one machine, in temporary state: mail delivered; a hold taken in one worktree made hold check exit 3 in the other; the edit hook, fed a client edit event for the held file in the sibling worktree, answered with a denial naming the holder; and a shell write to that same file went through. Hook-created names are from the hook documentation, not from a client session in a worktree.
