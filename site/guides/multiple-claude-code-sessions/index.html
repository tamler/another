Multiple Claude Code sessions, one repository

Running the same client in parallel takes one extra step: by default, Another can't tell the sessions apart.

Getting started Install What is an agent?

The catch: one identity per client and project

A session hook acts as the client name within its project, so two Claude Code sessions started in the same checkout are both claude@shop. The same rule applies to Codex, Grok CLI and Cursor. Sharing an identity has three effects:

  • Holds don't separate them. A hold conflicts with other agents, so one session's check passes against the other's hold, and overlapping acquires both succeed.
  • The first session to end ends the agent. Its session-end hook releases every hold, including any the other session took, and marks claude@shop offline until the other session's next prompt.
  • A new-mail notice appears once. Whichever session has the next prompt gets it, and the other session hears nothing about that message. Cursor gets no prompt notices at all.

Give each session its own name

Register one identity per session, from the root of the repository. The names here are examples; pick ones that describe the work. Each line prints the agent's full address, such as parser@shop in a project with the slug shop, and the rest of this page uses those addresses.

another init
another agent register parser --program claude --project .
another agent register ui --program claude --project .

Then start each session with its name in the environment. Run these in separate terminals:

ANOTHER_AGENT=parser@shop claude
ANOTHER_AGENT=ui@shop claude

Hooks use that name in place of the default. The agent has to be registered first. A bare name such as parser stops resolving once another project registers the same name. With an unknown or ambiguous name, the hook fails open and the session gets no digest. The first line of the session-start digest names the identity, such as parser@shop, so check it in each session.

MCP tools take the identity as an argument, so a session passes its own name, such as {"agent": "parser@shop"} to fetch_inbox. MCP messaging lists the arguments.

Mail and holds between the two

With distinct names, these work as they do between different clients:

another send --from parser@shop --to ui@shop --subject "API change" --body "Renamed fetch_user."
another inbox --agent ui@shop
another hold acquire --agent parser@shop --project . 'src/parser/**'
another hold check --agent ui@shop --project . 'src/parser/lex.rs'

The check exits with status 3 on a conflict. When ui ends its session, parser keeps its hold. Holds are still advisory: they show intent, and nothing stops a session writing to a held file.

Or use a worktree per session

Sessions in separate git worktrees get separate names without ANOTHER_AGENT, such as claude@shop and claude@shop-ui, because each worktree is its own project. They also get separate files. The trade-off is that holds no longer conflict across worktrees unless you share a project scope.

When a bare name stops resolving

Names are unique per project, not per machine. A bare name such as codex works only while one agent on the node has it. Register the same name in a second repository and every command still passing the bare name stops with an ambiguous error. This run was captured from another 0.1.0 built from 5ec0a58 in a temporary node with two throwaway repositories, shop and billing. Ids are as recorded. The full walkthrough, including a second repository that is also called shop, is in the repository at docs/ADDRESSING.md.

$ another agent list
claude@shop              claude    active   last seen 2026-11-12T09:39:52.213Z
codex@billing            codex     active   last seen 2026-11-12T09:39:52.230Z
codex@shop               codex     active   last seen 2026-11-12T09:39:52.222Z
$ another inbox --agent codex
another: agent name "codex" is ambiguous: it is registered in several projects; use name@project, one of: codex@shop, codex@billing
$ another send --from claude --to codex --subject "Review the invoice parser" --body "src/invoice.rs"
another: agent name "codex" is ambiguous: it is registered in several projects; use name@project, one of: codex@shop, codex@billing

Both exit with status 1 and nothing is sent. The acting agent and the recipient resolve the same way, so --agent, --from and --to all fail alike. The error lists the candidates; copy one. The mail then lands in the named project and nowhere else.

$ another send --from claude@shop --to codex@billing --subject "Review the invoice parser" --body "src/invoice.rs"
sent 01M77J1FT561NTTVYQPS8FBM9S to codex@billing
$ another inbox --agent codex@billing
codex@billing: 1 unread (0 urgent), 0 awaiting ack, 0 request(s)
   new  2026-11-12T09:39:52.261Z  claude@shop      Review the invoice parser  [01M77J1FT561NTTVYQPS8FBM9S]
$ another inbox --agent codex@shop
codex@shop: 0 unread (0 urgent), 0 awaiting ack, 0 request(s)

Set ANOTHER_AGENT to the full address and the flags can stay off. The installed hooks already act as client@project, so two sessions in two repositories never collide on their own; the bare name is what a person or a script types. name@project names a project on this node. An agent on a paired node needs name@project@node; the project part alone does not pick between two nodes that both have a codex@shop.

What this page rests on

We ran the another commands above in temporary state: init, agent register, send, inbox, hold acquire and hold check. We also fed session events to another hook run, the command the installed hooks call, with and without ANOTHER_AGENT set, and called fetch_inbox over another serve --stdio, with parser also registered in a second project. That is where the shared-identity effects and the digest line come from. We did not run the two claude start lines, so ANOTHER_AGENT reaching the hooks through the client's environment comes from the hook documentation, not from a client run. Another also does not start, supervise or assign work to these sessions; see how that differs from an orchestrator. The ambiguous-name section is a separate recorded run on 12 Nov 2026 with another 0.1.0 built from 5ec0a58; its output is copied as printed.
