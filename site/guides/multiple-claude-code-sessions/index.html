Multiple Claude Code sessions, one repository

Running the same client in parallel takes one extra step: by default, Another can't tell the sessions apart.

Getting started Install What is an agent?

The catch: one identity per client and project

A session hook acts as the client name within its project, so two Claude Code sessions started in the same checkout are both claude@shop. The same rule applies to Codex, Grok CLI and Cursor. Sharing an identity has three effects:

  • Holds don't separate them. A hold conflicts with other agents, so one session's check passes against the other's hold, overlapping acquires both succeed, and the edit hook lets each session edit the files the other is in.
  • The first session to end ends the agent. Its session-end hook releases every hold, including any the other session took, and marks claude@shop offline until the other session's next prompt.
  • A new-mail notice appears once. Whichever session has the next tool call or prompt gets it, and the other session hears nothing about that message. Cursor gets no prompt notices at all.

Give each session its own name

Register one identity per session, from the root of the repository. The names here are examples; pick ones that describe the work. Each line prints the agent's full address, such as parser@shop in a project with the slug shop, and the rest of this page uses those addresses.

another init
another agent register parser --program claude --project .
another agent register ui --program claude --project .

Then start each session with its name in the environment. Run these in separate terminals:

ANOTHER_AGENT=parser@shop claude
ANOTHER_AGENT=ui@shop claude

Hooks use that name in place of the default. The agent has to be registered first. A bare name such as parser stops resolving once another project registers the same name. With an unknown or ambiguous name, the hook fails open and the session gets no digest. The first line of the session-start digest names the identity, such as parser@shop, so check it in each session.

MCP tools take the identity as an argument, so a session passes its own name, such as {"agent": "parser@shop"} to fetch_inbox. MCP messaging lists the arguments.

Mail and holds between the two

With distinct names, these work as they do between different clients:

another send --from parser@shop --to ui@shop --subject "API change" --body "Renamed fetch_user."
another inbox --agent ui@shop
another hold acquire --agent parser@shop --project . 'src/parser/**'
another hold check --agent ui@shop --project . 'src/parser/lex.rs'

The check exits with status 3 on a conflict. When ui ends its session, parser keeps its hold. With the hooks installed, ui's edit to a file under that hold is stopped and parser@shop named; an edit from a shell command is not. File holds has the limits.

Or use a worktree per session

Sessions in separate git worktrees get separate names without ANOTHER_AGENT, such as claude@shop and claude@shop-ui, because each worktree is its own project. They also get separate files, and holds still conflict across worktrees of one repository, so the two find out before both edit the same path.

What this page rests on

We ran the another commands above in temporary state: init, agent register, send, inbox, hold acquire and hold check. We also fed session events to another hook run, the command the installed hooks call, with and without ANOTHER_AGENT set, and called fetch_inbox over another serve --stdio, with parser also registered in a second project. That is where the shared-identity effects and the digest line come from. We did not run the two claude start lines, so ANOTHER_AGENT reaching the hooks through the client's environment comes from the hook documentation, not from a client run. Another also does not start, supervise or assign work to these sessions; see how that differs from an orchestrator.
