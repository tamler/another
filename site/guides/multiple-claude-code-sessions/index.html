Session hooks derive a separate actor for each supported client session.

Getting started Install What is an agent?

A separate actor for each session

A supported hook uses the client session ID, project and base name to derive its actor. The start digest names the full address. Check the actual client and hook coverage before relying on it:

  • Holds distinguish session actors. Another checks a client edit against the other actor's holds when the guard runs and the client honors its response.
  • Unfenced end hooks leave holds alone. A hold remains until expiry or explicit release, so a delayed hook cannot release a resumed session's hold.
  • Mail belongs to the addressed actor. Mail sent to a legacy base address is not moved to the new session address. Cursor gets no prompt notices.

Use the address shown at start

Start two client sessions after installing their hooks. Each start digest names its full session address. A client must supply a stable session ID to the hook; missing or invalid IDs cannot safely use a shared base. Setting ANOTHER_AGENT before the client starts selects a base name, not the final session address.

For commands outside the hook, pass the exact address shown in the digest or run another session exec --agent <full-address> -- <program> so child commands inherit it. The hook cannot change the environment of its parent shell. MCP tools also need the full address; MCP messaging lists the arguments. The address is an identifier, not authentication.

Mail and holds between the two

Use the full addresses from the two digests as the sender and recipient for another send, another inbox and hold commands. A conflicting hold check exits with status 3. Hook End does not release holds because a resumed session can reuse the same ID; holds expire at their TTL or the exact actor releases them explicitly. Shell edits do not pass through the edit hook. File holds has the limits.

Or use a worktree per session

Sessions in separate git worktrees have separate files and project identities. Holds still conflict across worktrees of one repository, so the sessions can find out before both edit the same path.

When a bare name stops resolving

Names are unique per project, not per machine. A bare name such as codex works only while one agent on the node has it. Register the same name in a second repository and every command still passing the bare name stops with an ambiguous error. This run was captured from an untagged source build reporting another 0.1.0 at 5ec0a58 in a temporary node with two throwaway repositories, shop and billing. There is no v0.1.0 release tag. Ids are as recorded. The full walkthrough, including a second repository that is also called shop, is in the repository at docs/ADDRESSING.md.

$ another agent list
claude@shop              claude    active   last seen 2026-11-12T09:39:52.213Z
codex@billing            codex     active   last seen 2026-11-12T09:39:52.230Z
codex@shop               codex     active   last seen 2026-11-12T09:39:52.222Z
$ another inbox --agent codex
another: agent name "codex" is ambiguous: it is registered in several projects; use name@project, one of: codex@shop, codex@billing
$ another send --from claude --to codex --subject "Review the invoice parser" --body "src/invoice.rs"
another: agent name "codex" is ambiguous: it is registered in several projects; use name@project, one of: codex@shop, codex@billing

Both exit with status 1 and nothing is sent. The acting agent and the recipient resolve the same way, so --agent, --from and --to all fail alike. The error lists the candidates; copy one. The mail then lands in the named project and nowhere else.

$ another send --from claude@shop --to codex@billing --subject "Review the invoice parser" --body "src/invoice.rs"
sent 01M77J1FT561NTTVYQPS8FBM9S to codex@billing
$ another inbox --agent codex@billing
codex@billing: 1 unread (0 urgent), 0 awaiting ack, 0 request(s)
   new  2026-11-12T09:39:52.261Z  claude@shop      Review the invoice parser  [01M77J1FT561NTTVYQPS8FBM9S]
$ another inbox --agent codex@shop
codex@shop: 0 unread (0 urgent), 0 awaiting ack, 0 request(s)

For CLI commands, set ANOTHER_AGENT to the exact full address and the flags can stay off. Hooks derive session-specific addresses and show them in the start digest. name@project names a project on this node. An agent on a paired node needs name@project@node; the project part alone does not pick between two nodes that both have a codex@shop.

What this page rests on

Automated tests feed isolated session events directly to another hook run and check distinct actors and delayed End behavior. They do not establish that a particular live client supplies stable session IDs or enforces hook responses. Verify the actual client and version before relying on this coverage. Another does not start, supervise or assign work to these sessions; see how that differs from an orchestrator. The ambiguous-name section is a historical run on 12 Nov 2026 with an untagged source build reporting another 0.1.0 from 5ec0a58; its output is copied as printed.
