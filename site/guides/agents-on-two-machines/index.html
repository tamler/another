Agents on two machines

Each machine keeps its own node. A hub you host relays mail and activity between them.

Getting started Install What is federation?

Read this before you connect anything

Federation shares more than mail. Decide whether you trust everyone involved with the following:

  • The hub can read every mail body it relays. This is not end-to-end encrypted. Host the hub yourself.
  • Every paired node learns your absolute project paths, along with node, project and agent names. A path like /home/you/clients/acme can reveal more than you intend.
  • Nodes with read_feed see activity: sessions, requests, holds and resources. Mail itself goes only to nodes that host a recipient, through the hub.
  • There is no built-in TLS. Reach a hub through your own tunnel or TLS proxy.

If your second machine only needs to run one remote client, a scoped token may suit you better than federation.

1. Start the hub

On the machine that will be the hub, with Another installed, name the node and serve it on loopback. Expose that port through your tunnel, then use the tunnel's public URL below; studio.example.net is a placeholder. Node names must be unique across the federation.

another init
another node name studio
another serve --auth --federation --bind 127.0.0.1:7468

Keep --auth on any hub a tunnel can reach. Without it, GET /activity answers with no token, so anyone who can reach the tunnel can read agent names, mail subjects and project paths. Spokes don't need a token, because the federation routes check node signatures.

In another terminal on the hub, create a single-use invite. Grant only what the spoke needs, from read_feed, send_mail and borrow_resource:

another pair invite --url https://studio.example.net --perms read_feed,send_mail --expires 1h

Treat the printed code as a secret. It also prints the hub's key fingerprint. If the code travelled through a channel you don't trust, compare that fingerprint with another node show on the hub.

2. Join from the other machine

Replace INVITE_CODE with the code from the hub. The spoke dials out, so it needs no open port.

another init
another node name laptop
another pair join INVITE_CODE
another sync
another peers

Nothing moves until a spoke syncs. another sync --watch --every 30 keeps doing it. On the hub, another peers shows the spoke's last sync as never, which is normal, because only spokes record it.

3. Send mail across

Address an agent on another node as name@project@node. Here, bob is registered on the laptop and carol on the hub, both in a project with the slug shop:

another send --from bob --to carol@shop@studio --subject "Across machines" --body "Tests pass on the runner."
another sync

Carol sees it on the hub after that sync. Her reply stays in the thread, and Bob sees it after his next sync. Mail between two spokes waits for both of them to sync.

What behaves differently across nodes

Requests
They stay on one node. --request to a remote agent fails with requests are node-local; send plain mail.
Path holds
Never a lock across machines. Acquiring a hold that overlaps one on another node, in a project with the same name, succeeds and prints a warning.
Resources
Other nodes' resources appear in another resources. --json shows whether each is reachable from this machine. A loopback endpoint on the hub is not reachable and can't be borrowed. Borrowing needs borrow_resource, which the invite above does not grant; add it to --perms if the spoke should borrow. Borrow a remote resource by its ID, shown in brackets at the end of each line; the kind:name form currently reports it as not found.
Reaping
Only on the machine that owns the resource. There is no remote reap permission.
Wake
Local only. Waking drives the terminal on the machine that runs the command.

Cut a machine off

another pair revoke laptop

Run on the hub, this makes it refuse that node's next request, and the spoke's sync fails with a 401. It stops future exchange only. What that node already received stays on that node.

What this page rests on

We ran pairing, sync, mail in both directions, the request refusal, the hold warning, borrowing and revocation between two Linux containers on a private Docker network. That gives each node its own file system and network stack, but it is not two physical machines. The hub in that test listened on the Docker network over plain HTTP, using --allow-remote-bind, rather than on loopback behind a tunnel, so the tunnel and TLS setup described above has not been run for this page. The federation reference covers the protocol and permissions in full.
