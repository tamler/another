You may not need this

Several simpler or bigger options do part of Another's job. Some will suit you better.

Coordination or orchestration Alternatives

Relaying by hand

You copy one agent's output into the other's prompt. It needs no setup, and you read everything that crosses. For an occasional second opinion, this is the right choice.

It stops working when the relay fills your day, or when an agent needs an answer while you are away.

A shared markdown file

Agents append to something like HANDOFF.md. It is readable, works with any client and lives in Git if you want it to. For one sequential handoff between two agents, it is often enough.

The file has no recipients, no read state and no owner for a task. Agents have to remember to reread it, and two editing at once can overwrite each other. Stale instructions stay there until someone removes them.

Git worktrees alone

Giving each agent its own checkout prevents most edit collisions, with tools you already have. If the agents never need to talk until you merge their branches, you are done.

Worktrees don't carry messages, so one agent won't hear that another changed an API until the merge. The two tools fit together: here is how Another treats worktrees, including how holds cross them.

Features built into your client

If every agent you run is Claude Code, try its own features first. They are integrated and need nothing extra:

Subagents
Helpers with their own context, working within a single session. Good for a focused task where only the result matters.
Agent teams
Several Claude Code sessions with a lead, a shared task list and direct messages. Experimental and off by default, with one team per session and documented limits on resuming.
Cross-session messaging
Passes findings between Claude Code sessions you run yourself.

Another fits when the agents are different programs, such as Claude Code and Codex, or when you want mail and leases to outlast a session in a database you can inspect. Other clients may have similar features; we have not surveyed them here.

Other MCP coordination tools

agent-bus-mcp
A stdio MCP server backed by SQLite, built around named topics that peers join. MIT license. Its model is closer to a chat channel than an inbox, and its smaller surface may be all you want.
mcp_agent_mail_rust
A larger MCP server that keeps its records in Git and has its own terminal and web interfaces. Worth a look if you want those. Its license is MIT with an added rider, so read the terms first.

We describe these from their public summaries and have not benchmarked them. Another shares no code with them. The scope comparison sets them side by side.

File claims that can deny an edit

Another's another hold check is advisory: it exits 3 on overlap and grants nothing. Its edit hook is not. With the hooks installed, a Claude Code, Codex or Grok CLI edit to a file another agent holds is stopped and the holder named; an edit from a shell command still gets through. A few other tools also document a Claude Code hook that can refuse the edit. I read their READMEs on 10 Nov 2026. I did not benchmark them against each other.

agent-coord
A JSON board at ~/.agent-coord/board.json. File locks and task claims. The README says a Claude Code PreToolUse hook can block an edit, and that Codex has no pre-tool hook, so Codex only cooperates if it calls the tools.
dibs
One static binary, no daemon. TTL file claims. The README says hooks can block a colliding edit, and that lessons live as markdown in the repo.
claude-agent-sync
Python standard library and a SQLite file in the repo (.claude/coordination/state.sqlite). The project says a PreToolUse hook fails closed on a lock conflict. There is a console for watching the sessions.
AgentRelay
Task leases are exclusive while they are active. File-scope claims warn. The README says they do not stop an edit made outside MCP. It also documents a guarded tmux read and send.
Coordinaut
Claim a task and a file scope, then heartbeat. The README argues agents should not coordinate by racing to edit one markdown file. The markdown it generates is a view. The log is the state.

If you want mail across Claude Code and Codex, plus a hook that stops a client edit to a held file, that is the job I built Another for. If you need every write stopped, including one from a shell, none of these do that; use separate checkouts. Read the current hook docs for your client before you pick one. I have not measured which one is faster.

Orchestrators

If you want software to plan the work, start the agents and give each one a branch, you want an orchestrator, and Another won't do that. Agent Orchestrator is one example: its README describes a desktop workspace in which a main agent plans the work and starts a worker per task, each with its own branch and worktree.

Another starts nothing. It suits people who already run their agents and want them to talk. The two can coexist.

When Another is the wrong choice

  • You run one agent at a time. There is nobody to coordinate with.
  • You need a real lock. The edit hook stops a client edit to a held file, but an edit from a shell command still gets through, and nothing guards a commit. Use separate checkouts and review the merge.
  • You need instant delivery. Hooks fire at session start, after the next tool call and on the next prompt. A loopback daemon wakes idle Herdr agents, and wake adapters can type into an idle terminal, but nothing interrupts an agent mid-task.
  • You need end-to-end encrypted mail. The database is ordinary SQLite, and a federation hub can read what it relays.
  • You want a signed, packaged release. There is no release yet, so you build from source, and planned binaries are unsigned.

When it does fit

You run two or more different coding clients side by side, you are tired of being the relay, and you are comfortable with a young open source tool. Try it in temporary state, which changes no client configuration, before you commit to anything.
